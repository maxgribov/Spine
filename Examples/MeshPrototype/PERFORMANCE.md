# Уменьшение overdraw и замеры — 2026-10-03

Прямоугольники отрисовки теперь ограничены границами отдельных треугольников. На официальном Goblins Pro площадь этих прямоугольников уменьшилась в **6–8 раз**, GPU-время — в **1.6–2.2 раза**. Частота обновлений сцены не выросла: на 50 персонажах пример ограничен CPU, а новая подготовка экранных координат немного увеличивает CPU-стоимость.

Это оптимизация изолированного прототипа. Основная библиотека Spine не изменена.

## Результат измерений

Apple M1 Max, macOS 26.6, Swift 6.3.3, Release. Все 12 сценариев завершены; скрытых/перекрытых кадров по `NSWindow.occlusionState` — 0, thermal state в начале и конце всех сценариев — nominal.

В таблице CPU/GPU — **среднее двух медиан** независимых раундов с обратным порядком режимов, а не медиана объединённых выборок. CPU включает pose, geometry и подготовку framebuffer-матриц в SKView. GPU измерен отдельно через SKRenderer на target 1920×1080.

Разница между одной и несколькими фигурами объясняется составом сцены: одна — goblin; 10/50 — поровну goblin/goblingirl. Их topology и доля region attachments отличаются. Масштаб персонажа во всех нагрузках фиксирован: 0.65. Персонажи размещены регулярной сеткой; при большой нагрузке части фигур могут перекрываться.

Площади — геометрическая оценка работы растеризатора, **не измеренный счётчик GPU fragments**. Сумма площадей треугольников в обоих режимах совпадает. Отношение quad/triangle area для смешанных сцен снизилось приблизительно с 19.9 до 3.3; это не коэффициент покрытия уникальных пикселей с учётом прозрачности.

На 50 персонажах `sceneUpdateAndEncodeCPU` в отдельном SKRenderer-стенде составляет около 31 мс в старом и 32 мс в новом режиме. Поэтому сокращение GPU-времени примерно на 0.65 мс не устраняет CPU-ограничение. CPU pose из SKView и encoding из SKRenderer получены в разных трактах: их сумму нельзя выдавать за измеренную длительность кадра SKView.

Сырые данные с mean/p50/p95/max: [12 измерений](Benchmarks/2026-10-03-m1-max.json). В частности, для 50 персонажей CPU подготовки увеличился примерно на 14%; это измеренная цена текущей реализации, а не общий выигрыш производительности приложения.

## Изменение renderer

Доступны `BoundsMode.mesh` (контрольный вариант) и `.triangle` (новый режим по умолчанию). В новом режиме:

1. Для каждого треугольника вычисляется его AABB с защитным отступом около одного framebuffer-пикселя, переведённым в локальные координаты.
2. Shader получает единую для mesh матрицу преобразования `gl_FragCoord` в нормализованные координаты mesh. У соседних треугольников одинаковый вход для проверки общих рёбер.
3. Поза и положение в окне обновляются раздельно: `updatePositions`, затем `prepareForRendering(localToPixels:)` перед рисованием. Изменение только переноса обновляет uniforms; изменение масштаба/поворота также пересчитывает padding.
4. Нулевой/нечисловой transform скрывает геометрию; после восстановления transform она снова отображается. Узлы между кадрами переиспользуются.

Простое уменьшение sprite bounds с восстановлением общей координаты через локальный `v_tex_coord` давало двойную прозрачность на отдельных пикселях движущихся рёбер. Поэтому этот вариант не оставлен основным. Новый подход требует актуальной матрицы render target: это дополнительный контракт интеграции, а не полностью прозрачная замена произвольного SKNode.

У native Metal framebuffer и SKRenderer начало fragment coordinates сверху слева; у проверенного пути `SKView.texture(from:crop:)` offscreen target перевёрнут. `RasterCoordinates.swift` учитывает эту разницу. Матрицу одного target нельзя использовать для другого. Встроенные offscreen passes эффектов/масок не поддержаны автоматически; для них сохранён прежний `.mesh` режим.

Число узлов и треугольников не сокращено. Производительность CPU и batching пока отдельно не оптимизировались.

## Проверки корректности

- 6 unit tests: некорректная topology/поза, восстановление вырожденного треугольника, сокращение quad area без изменения triangle area, восстановление singular projection, изменение padding при pixel density.
- 10 базовых GPU-сценариев: 9 совпали побитово. В повернутом nearest-тесте 2 пикселя выбрали соседний texel при совпадающем alpha. Такие пиксели считаются отдельно; это **не** точное совпадение всего изображения.
- 128 сравнений движущихся сеток и Goblins: нет внутренних расхождений >2/255; зарегистрированы 45 однопиксельных отличий на существующих границах прозрачности. Допуск на них ограничен диапазоном непосредственных соседей эталона. Дыры/двойное alpha внутри одноцветного fan этот допуск не пропускает.
- Сверка поз и UV с `@esotericsoftware/spine-core@4.1.56`: 16 poses, 6064 координаты, максимум ошибки позиции 0.0001741 единицы Spine, UV — 5.96e-8.
- Для benchmark дополнительно сравниваются сохранённые кадры обоих режимов из **самого измеряемого SKRenderer target**. Во всех двух раундах для 1 персонажа — 0 пикселей с отличием >4/255, для 10 — 1, для 50 — 6 из 489 283 foreground pixels. Это диагностическая проверка полноты/совпадения рендера, не замена строгих seam-тестов. [Результаты](Benchmarks/2026-10-03-image-validation.json).

Контрольные GPU-кадры на 50 персонажах просмотрены: оба режима действительно рисуют персонажей по всей сцене. Снимки раннего стенда с неправильным направлением Y новая проверка отклоняет. Их оптимистичные GPU-числа в итоговые данные не включены. Сумма alpha не годится для такой проверки: фон target непрозрачен; сравниваются цветные изображения.

## Методика и воспроизведение

```sh
swift run -c release --package-path Examples/MeshPrototype MeshPrototype --verify Examples/MeshPrototype/output
swift run -c release --package-path Examples/MeshPrototype MeshPrototype --benchmark Examples/MeshPrototype/output/benchmark
```

В benchmark два раунда, порядок modes меняется на обратный. SKView получает 30 warmup + 120 measured frames на сценарий, SKRenderer — 30 + 60. Animation time детерминирован по номеру кадра и индексу персонажа, а не по wall clock; оба режима обрабатывают одинаковые позы.

SKView запрашивает 60 FPS, размер view 960×540 points при backing scale 2. `effectiveFPS` в JSON означает частоту callbacks сцены, не подтверждение фактической презентации каждого GPU-кадра. Потерянные drawables/системный планировщик могут влиять на отображение.

GPU-время берётся из завершённых `MTLCommandBuffer.gpuStartTime/gpuEndTime`. Для изоляции командные буферы исполняются последовательно. `serializedWall_ms` включает ожидание и не переводится в FPS. Диагностический readback/PNG выполняется после timed samples. GPU target — `.bgra8Unorm`, 1920×1080; результат характеризует этот стенд, не напрямую внутренний GPU pass SKView.

App Nap предотвращается через `ProcessInfo.beginActivity`, окно benchmark временно floating. Регистрируются occlusion и thermal state. Ранний запуск без этих условий имел сильный дрейф CPU-времени и исключён из итогового сравнения. Другие приложения/системные процессы полностью не изолированы; два повторения на одной машине не являются статистическим исследованием всех устройств.

Проверка уже сохранённых GPU-кадров без повторения замеров:

```sh
swift run -c release --package-path Examples/MeshPrototype MeshPrototype --validate-benchmark Examples/MeshPrototype/output/benchmark
```

Стенд автоматически запускает эту проверку перед сообщением `BENCHMARK COMPLETE`. Полный комплект — 12 записей `benchmark.json`, 12 GPU PNG и `image-validation.json`. JSON в `Benchmarks/` сохранён из итогового замера; PNG и промежуточные невалидные прогоны остаются в игнорируемом `output/`.

## Следующий приоритет

Для этой сцены следует сокращать **CPU-стоимость**, а не только площадь отрисовки: заранее компилировать fixture timelines/lookup в типизированные структуры, уменьшать работу с attributes на кадр, исследовать разделение общего shader и per-node state, измерять batching и реальные draw calls. Последние сейчас не измерены; число треугольников нельзя использовать вместо draw calls.

Требуются отдельные проверки iOS/tvOS/watchOS, real-device GPU time и интеграции с основным `Skeleton`. Ускорение GPU на M1 Max не означает готовность полной поддержки meshes или обещание 60 FPS для 50 персонажей.
