# Композиция skins без прерывания анимации

## Цель

Определить, какие способы композиции удовлетворяют [заданию](task.md), и какие решения нужно принять перед ADR. Основная неопределённость — как отличать наследование, замену и скрытие во всех состояниях анимации, сохраняя атомарность смены комплекта.

Наиболее перспективный кандидат — полный комплект из упорядоченных слоёв с явной областью замены и скрытия. Простого объединения skins недостаточно. Это рекомендация для обсуждения, а не утверждённый контракт или план реализации.

## Основания и границы исследования

Проверен код ревизии `52e713e6458963ed6723b6cacf829352c4cd0e76`, совпадающей с указанной в задании. Изучены runtime, renderer, compiler, публичные skins API и существующие тесты. Контекст соседнего проекта подтверждает region-only сценарий через `SpineMeshAsset`; библиотечные fixtures не должны зависеть от него.

Формат остаётся Spine 4.1, renderer — SpriteKit, рабочие платформы compiled-пути — macOS/iOS. В этой работе код не менялся, приложение и тесты не запускались, стоимость переключения не измерялась. Наличие теста ниже означает существующее покрытие, а не подтверждение его прохождения в этой сессии.

## Что означает skin

Skin связывает пару «слот + имя placeholder» с attachment. Placeholder — логическое имя состояния, например `hand-open`; оно не обязано совпадать с именем картинки. Один skin может содержать несколько частей предмета. В официальном runtime поиск при отсутствии записи обращается к `default`: удаление записи само по себе не означает устойчивое скрытие. [Spine Runtime Skins](https://esotericsoftware.com/spine-runtime-skins).

В официальной ветке 4.1 `addSkin` переносит ссылки на attachments, более поздняя запись заменяет предыдущую с тем же ключом. Разные имена одного слота остаются разными записями. Это полезный прецедент для приоритетов и разделяемых ресурсов, но не готовая реализация требуемого гардероба. [Skin.ts, ветка 4.1](https://github.com/EsotericSoftware/spine-runtimes/blob/4.1/spine-ts/spine-core/src/Skin.ts).

Общие placeholders позволяют переиспользовать клипы между нарядами. Порядок skins не задаёт перекрытие картинки: переднюю и заднюю части шляпы нужно заранее расположить в соответствующих слотах. В полном Spine skins также включают условно активные кости и constraints; это отдельные возможности, которые нельзя обещать вместе с объединением attachments. [Spine Skins](https://en.esotericsoftware.com/spine-skins).

Локальный compiled-путь отклоняет skin bones и skin constraints при проверке экспортированных данных, а также неподдерживаемые constraints/clipping. Их добавление не требуется для этой задачи. [SpineFeatureIssue.swift](../../Sources/Spine/Model/SpineFeatureIssue.swift), [MeshAssetCompiler.swift](../../Sources/Spine/Mesh/Compilation/MeshAssetCompiler.swift).

## Что уже есть и чего недостаёт

| Наблюдение в коде | Последствие для решения |
|---|---|
| `applySkin` готовит следующий renderer и копии состояний до замены живых объектов | Есть основа для атомарного применения, но нужно расширить валидацию и согласовать момент готовности изображения |
| Runtime и renderer независимо объединяют `default` с одним skin | Оба потребителя должны получать согласованный результат композиции; изменение только runtime недостаточно |
| `activeName` становится nil при неизвестном имени; смена skin использует `old ?? fallback` | Сейчас не сохраняется причина отсутствия картинки; возможен возврат setup attachment вместо текущего состояния |
| Смена skin не изменяет epoch и execution; курсор событий продвигается до callback | Сохранение работающего action возможно без пересоздания, но реентрантность нужно проверять отдельно |
| Renderer создаёт объекты для всех возможных attachments выбранного lookup | Стоимость зависит от числа доступных состояний, не только от видимых предметов |
| Все skins, ресурсы и клипы компилируются заранее | Композиция не даёт ленивую загрузку; ошибка ненадетого ресурса может остановить создание asset |
| Compiler проверяет имя attachment timeline по всем skins | Валидный asset не гарантирует, что выбранный комплект покрывает все состояния клипа |

Основания: [MeshRuntime.swift](../../Sources/Spine/Mesh/Runtime/MeshRuntime.swift), [MeshSlotState.swift](../../Sources/Spine/Mesh/Runtime/MeshSlotState.swift), [MeshSetupRenderer.swift](../../Sources/Spine/Mesh/Renderer/MeshSetupRenderer.swift), [MeshAssetCompiler.swift](../../Sources/Spine/Mesh/Compilation/MeshAssetCompiler.swift).

В документе «база» означает исходную внешность персонажа; это не обязательно экспортный skin `default`. «Полный комплект» — весь выбор приложения для одного Skeleton, включая отсутствие предметов. Командный вариант — заранее подготовленные attachments нужного цвета. Автоматическое включение `default` или передача базы явным слоем остаётся вопросом контракта.

## Кандидаты композиции

| Подход | Возможности | Цена и риск | Пригодность |
|---|---|---|---|
| Только объединение skins по порядку | Просто собрать несколько независимых предметов | Нет явного скрытия; старые состояния слота остаются доступны | Недостаточен самостоятельно |
| Упорядоченные слои + явная замена/скрытие области | Независимые предметы, контролируемое наследование, защита от старых состояний | Требует договориться о границах области и конфликтах | Предпочтительный кандидат |
| Полная итоговая таблица «слот + состояние → attachment/скрыто» от приложения | Максимальный контроль, явный результат | Приложение вынуждено знать все состояния и дублировать правила сборки | Возможен как низкоуровневый путь, дороже для клиента |

Готовые skins для всех сочетаний и смена текстуры текущего sprite не подходят: первое противоречит заданию и разрастается с каталогом, второе не учитывает размещение, несколько частей предмета и будущие ключи анимации.

Передача полного комплекта естественно выражает атомарность. Последовательные команды «надеть/снять» удобны, но требуют накопления состояния или транзакции, иначе промежуточные комплекты видимы. Категории магазина и командные варианты остаются на стороне приложения.

### Область замены важнее порядка слоёв

Пример: база содержит `hand/open` и `hand/closed`, предмет заменяет только `open`. Даже при правиле «последний слой побеждает» ключ `closed` вернёт базовую кисть. Поэтому нужны два разных намерения: дополнить отдельные состояния или полностью заменить заданную область.

| Область | Преимущество | Ограничение |
|---|---|---|
| Весь слот | Все его состояния защищены от возврата нижних слоёв; удобно снять серьгу | Слишком широко, если слот используется для разных назначений |
| Отдельный placeholder | Точная замена и скрытие | Нужно перечислить все состояния вещи; новые состояния легко пропустить |
| Явный набор слотов/placeholders | Подходит для предметов из нескольких частей | Нужны проверка имён и понятные правила пересечения |

Рекомендация для ADR: рассмотреть слот как основную область полной замены, точечные переопределения — как отдельную возможность. Не выводить область автоматически только из записей skin: неполный skin не сообщает, что автор хотел скрыть.

Детерминированное правило «более поздний слой выигрывает» знакомо по Spine. Альтернатива — отклонять пересечения как ошибку; это помогает находить случайные конфликты, но усложняет намеренные командные overrides. Скрытие может быть операцией в том же порядке либо окончательной маской поверх всех слоёв: оба варианта допустимы, но дают разные результаты при последующей замене.

## Скрытие, отсутствие состояния и непрерывность клипа

Для выполнения задания необходимо различать три факта: что запросила анимация, что разрешает комплект и какой attachment реально выбран. Например, при скрытой серьге анимация может сменить `front` на `side`; после снятия скрытия нужен `side`, а при анимационном nil серьга должна оставаться невидимой. Это вывод из требований, не выбранная структура данных.

Официальное руководство показывает обновление skin через setup slots и повторное применение animation state. В локальном runtime sampling также доставляет события, а setup сбрасывает позу, цвет, порядок и время. Копировать такую последовательность буквально здесь нельзя: нужен способ обновить внешний вид без повторного проигрывания. [Runtime Skins: Skin changes](https://esotericsoftware.com/spine-runtime-skins), [MeshRuntime.swift](../../Sources/Spine/Mesh/Runtime/MeshRuntime.swift).

Отсутствующее состояние требует отдельного решения:

| Политика | Пользовательский эффект | Цена |
|---|---|---|
| Скрывать отсутствующее состояние | Никогда не показывается случайный базовый предмет | Неполный предмет может исчезнуть во время движения |
| Отклонять неполный комплект заранее | Ошибка обнаруживается до смены внешности | Нужно определить набор обязательных состояний: setup, текущий клип или все клипы |
| Наследовать из нижних слоёв | Удобно для намеренно частичных overlays | Нельзя применять внутри области полной замены/скрытия без нарушения задания |

Рекомендация: явно разрешённое наследование отделить от ошибки неполного предмета. Выбор между скрытием и предварительным отказом остаётся открытым. Проверка только текущего состояния не защищает от следующего ключа или нового клипа; если новые клипы могут отклоняться, это тоже часть будущего контракта.

Смена из event callback особенно важна: callback вызывается после обновления slots и продвижения курсора событий. Композиция не должна менять идентичность проигрывания или повторно сэмплировать клип. Нужно проверить событие на последнем кадре, несколько событий с одинаковым временем, повтор и обработку ошибки внутри callback.

## Атомарность, ресурсы и совместимость

Атомарность имеет две границы: принятие комплекта и подготовка его изображения. Сейчас `applySkin` меняет renderer, а окончательные transforms, видимость, tint и draw order обновляются в `prepareMeshes`. Документация требует вызывать подготовку последней в `didFinishUpdate`, в том числе после изменений на паузе. Следовательно, «API успешно вернул управление» ещё не доказывает готовность следующего изображения. [Meshes.md](../../Sources/Spine/Documentation.docc/Meshes.md).

Для ADR есть два варианта: гарантировать логическую атомарность с обязательным следующим prepare либо готовить изображение до commit в допустимой фазе кадра. Второй вариант сильнее, но зависит от актуального render context и сложнее при physics. Ошибки входного комплекта должны оставлять старое состояние; ошибки окружения кадра уже имеют собственный контракт скрытия renderer. Эти классы ошибок нельзя смешивать.

Безопасный кандидат — сериализовать применение в том же контексте, где обновляется сцена, до финального prepare; callback события входит в этот путь. Произвольные конкурентные вызовы и изменение после prepare без повторной подготовки не следует обещать. Точную допустимую фазу и правила вызова предстоит закрепить.

| Стратегия объектов | Преимущество | Цена |
|---|---|---|
| Подготовить новый renderer целиком, затем заменить старый | Ближе к текущему атомарному пути, проще откат ошибки | Временное удвоение объектов, потеря идентичности attachment nodes |
| Обновлять только изменившиеся attachments | Меньше аллокаций, больше сохранённых ссылок | Сложнее откат, очистка point/physics и согласование proxy bones |
| Кэшировать renderers комплектов | Быстрое повторное применение | Рост памяти по комбинациям, усложнение владения |

Рекомендовано начать оценку с полной замены renderer при сохранении compiled IDs, текстур и материалов; необходимость более сложного переиспользования подтвердить измерениями. Неограниченный кэш комбинаций непригоден. Повтор одинакового комплекта должен обходиться без накопления объектов, но критерий равенства требует решения о дубликатах и порядке слоёв.

Требование задания — сохранить контракт старых публичных single-skin методов и legacy-пути, а ошибки нового API делать диагностируемыми. Рекомендация исследования — явно отклонять новый API на legacy Skeleton; это допустимый вариант, а не уже принятое решение. При переходе обратно в single-skin нужно очистить правила композиции; сравнения только с прежней строкой `selectedSkin` недостаточно. Текущий `action(applySkin:)` подавляет ошибку применения через `try?`; переносить это в новый API без диагностического канала нельзя. [Skeleton+Skins.swift](../../Sources/Spine/Extensions%20Public/Skeleton+Skins.swift).

## Какие attachments включать в первую версию

| Тип | Что известно | Риск новой композиции |
|---|---|---|
| Region | Уже поддержан compiled-путём; обязательный сценарий | Placement, trim, цвет, все состояния и несколько частей |
| Point | Есть логические узлы и выбор active points | Старые внешние ссылки и дублирование узлов |
| Bounding box | Есть владение physics и reconciliation | Замена тела, скрытие и остаточные transforms физики |
| Mesh / linked mesh | Есть compiled geometry и связь с источником deform | Перенос deform на чужую геометрию; восстановление после скрытия |

Две разумные границы: region-only композиция с явным отказом на неподдерживаемом результате либо все уже поддержанные типы с расширенными проверками. Первая быстрее для гардероба, но нужно решить, допускается ли неизменяемая база с point/box/mesh. Проверять только текущую видимую картинку недостаточно: неподдерживаемый тип может появиться следующим ключом. Запрет всего asset из-за ненадетого mesh был бы существенно шире запрета композиции.

Для mesh совместимость задаётся существующим `deformSourceID`, а не именем PNG или совпадением числа вершин. При скрытии и возврате mesh текущий deform может потребовать отдельного восстановления без событий; это дополнительная цена поддержки, особенно на паузе. Linked mesh уже ссылается на скомпилированного родителя: присутствие родительского skin среди надетых слоёв само по себе не требуется для доступа к геометрии. [Compiler](../../Sources/Spine/Mesh/Compilation/MeshAssetCompiler.swift), [SlotState](../../Sources/Spine/Mesh/Runtime/MeshSlotState.swift).

## Как уменьшить оставшуюся неопределённость

Самодостаточная проба должна содержать базу, две шляпы из нескольких частей, два варианта одежды, серьгу, бандану и четыре подготовленных командных варианта. Хотя бы один слот имеет два разных placeholder, а клип — nil, color, draw-order и event ключи. Это проверяет то, чего один базовый skin матроса доказать не может.

Существующие [SlotStateTests](../../Tests/SpineTests/Mesh/SlotStateTests.swift), [AttachmentInteropTests](../../Tests/SpineTests/Mesh/AttachmentInteropTests.swift), [ActionLifecycleTests](../../Tests/SpineTests/Mesh/ActionLifecycleTests.swift), [LinkedMeshTests](../../Tests/SpineTests/Mesh/LinkedMeshTests.swift), [ResourceLifetimeTests](../../Tests/SpineTests/Mesh/ResourceLifetimeTests.swift) и [RendererProxyLifetimeTests](../../Tests/SpineTests/Mesh/RendererProxyLifetimeTests.swift) дают основу регрессий. Они не заменяют проверки композиции: снятие/возврат на паузе, будущий ключ отсутствующего состояния, отказ без изменения playback, callback завершения и два разных комплекта на общем asset.

Предлагаемое измерение: отдельно время применения и следующего prepare; первый вызов, повтор одинакового комплекта и длительное чередование. Фиксировать медиану/p95/максимум, число nodes/physics objects, вызовы texture provider и память после прогрева. Сравнить один и несколько Skeleton на общем asset, указав число слотов, доступных состояний, версию ОС и устройство. На физическом iPhone и macOS проверить изображение, sRGB/альфу и воспроизведение. Число фигур для игровой нагрузки вывести из правил матча. По заданию численные бюджеты разработчик предлагает после измерений. Для оценки их приемлемости владелец приложения должен предоставить целевые устройства, максимальную нагрузку матча, ожидаемую частоту переодеваний и допустимое влияние на кадр; до этого сравнение стратегий будет относительным.

## Открытые вопросы для ADR

1. Достаточно ли полного комплекта слоёв как публичного входа; нужен ли публичный снимок текущего комплекта? При подготовке ADR проверить кандидат API клиентскими примерами независимой замены, снятия и восстановления комплекта без internal-типов.
2. Каковы области полной замены и скрытия? Побеждает последний слой или пересечения считаются ошибкой; может ли более поздняя замена отменить скрытие?
3. Отсутствующее состояние скрывается или вызывает предварительный отказ? Если отказ — проверяем setup и все клипы либо заявленный приложением набор?
4. Что означают пустой комплект, повтор skin, явный `default` и отсутствие `default`? Пустой комплект восстанавливает базу или делает персонажа пустым?
5. Какие типы разрешены в результате композиции v1, включая неизменяемую базу? Как диагностировать тип, который появится только в будущем состоянии?
6. Когда commit считается завершённым относительно prepare и physics? Какие вызовы разрешены на паузе, из callback и после подготовки кадра?
7. Гарантируется ли идентичность только Skeleton/bones/slots или также неизменённых attachment nodes? Как клиент обновляет ссылки на points и physics после смены? Для существующих статических bounding boxes отдельно определить последствия пересоздания тела для контактов и внешних связей, включая скрытие/возврат; сохранение динамики, импульсов и уже доставленных контактов не предполагать автоматически и не расширять общий physics-контракт этой задачей.
