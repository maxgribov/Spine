# Композиция skins для гардероба персонажа

## Что требуется

Добавить в библиотеку возможность собрать внешний вид одного персонажа из нескольких
независимых наборов attachments и менять этот комплект во время проигрывания анимации.
Приложение должно уметь надеть шляпу, заменить одежду, снять серьгу или поменять оружие,
не пересоздавая персонажа и не создавая заранее skin для каждой комбинации предметов.

Это **задание на доработку**, не спецификация API и не план реализации. Конкретные
типы, сигнатуры, внутреннее устройство композиции и последовательность работ определяет
разработчик. Ниже зафиксированы ожидаемое поведение, ограничения и важные особенности
текущего кода. Нерешённые контрактные вопросы перечислены отдельно.

## Контекст использования

В игре у каждого типа персонажа собственные скелет и анимации. Матрос, капитан и
разведчица не используют общий риг. Однако все наряды **одного типа персонажа** должны
работать с его существующими idle, walk, attack и другими клипами без копирования анимаций.

Предполагаемый комплект:

```text
базовая внешность
  + выбранная одежда
  + головной убор
  + украшение либо его отсутствие
  + оружие / обувь / специальные детали роли
  + варианты командных деталей
```

В Spine отдельный предмет может быть отдельным skin. Один такой skin может содержать
несколько attachments: переднюю и заднюю части шляпы, корпус одежды и рукава и т. п.
Разные варианты предмета используют общие слоты, skin placeholders и точки крепления.
Термины `skin` и «полный костюм» не тождественны.

В приложении предмет привязан к определённому типу персонажа. Первоначальный ориентир —
10 предметов суммарно по категориям каждого типа; это не лимит библиотеки и не число
одновременно отображаемых персонажей. У матроса текущая сабля и держащая её кисть —
одна сменная деталь; независимая замена пальцев для этого ассета не нужна.

## Область доработки

- Обязательный путь интеграции: `SpineMeshAsset` → `Skeleton(meshAsset:skin:)`.
  Он уже используется прототипом для обычных region attachments, без meshes.
- Первая прикладная версия гардероба — region attachments и костные анимации.
  Плащи, deform, новые constraints, clipping и смешивание клипов для гардероба не нужны.
- Существующие mesh/linked-mesh/deform, point и bounding-box возможности библиотеки
  не должны регрессировать. Поддержку этих типов именно в **новой композиции** следует
  явно определить; недоступные сочетания должны давать понятную ошибку, не тихую порчу.
- Существующие single-skin вызовы и старый путь `Skeleton(json:folder:skin:)` должны
  сохранять совместимость. Расширять legacy-путь новой функциональностью необязательно;
  поведение нового API на таком экземпляре должно быть явно описано.
- Целевой формат данных остаётся Spine 4.1. Не требуется обновление формата,
  новый проигрыватель анимаций или переход со SpriteKit на другой renderer.

## Ожидаемое поведение

### Независимые предметы и полный комплект

Приложение передаёт выбранный комплект, а библиотека разрешает его в итоговый набор
attachments. Замена шляпы должна сохранить одежду, серьгу и командные детали.
Смена командного варианта не должна сбрасывать надетые вещи.

Необходимо различать три намерения:

- **Наследовать:** предмет не переопределяет соответствующую часть; действует база
  или другой разрешённый слой комплекта.
- **Заменить:** использовать attachment выбранного предмета.
- **Скрыть:** намеренно не показывать часть, даже если она существует в `default`
  или других skins. Например, снять серьгу или скрыть бандану под шляпой.

Отсутствия записи в skin недостаточно для выражения намеренного скрытия. После снятия
предмета базовая вещь не должна неожиданно появляться на следующем кадре, после reset
или начала следующего повтора клипа. При отмене скрытия должна восстанавливаться часть,
соответствующая текущему логическому состоянию анимации и новому комплекту.

Применение комплекта должно быть атомарным: все его части меняются вместе.
Если комплект некорректен, остаются прежние внешний вид и состояние воспроизведения,
а вызывающий код получает диагностируемую ошибку. Runtime не должен самостоятельно
подменять товар случайной базовой вещью при ошибке применения.

### Конфликты и порядок слоёв

Нужен детерминированный и документированный способ разрешать конфликт, когда несколько
skins задают одну и ту же пару «слот + attachment name». Это может быть объявленный
порядок приоритетов или другой явный контракт; случайный порядок обхода словаря недопустим.

Следует отдельно определить поведение для **разных attachment names одного слота**.
Простое объединение словарей может оставить базовые варианты, к которым позже вернётся
attachment timeline. Приложению нужен способ заменить/скрыть весь требуемый набор
состояний предмета, а не только картинку, которая видна в момент переодевания.

Предмет из нескольких частей должен занимать заранее предусмотренные слоты.
Порядок входных skins не должен неявно становиться порядком рисования. Существующие
slot order и draw-order timelines продолжают управлять перекрытиями изображения.

### Проверка контента до применения

Нужна публичная проверка комплекта без применения: для указанного compiled asset,
базы и слоёв действуют те же правила разрешения, полноты и диагностики, что при
надевании. Проверка не создаёт Skeleton или renderer-узлы, не меняет asset и живые
экземпляры. Она не обещает предсказать ошибки состояния сцены или render context.
Отдельный инструмент без текстур или поддержка Linux в эту задачу не входят.

Нужно публичное неизменяемое описание собственных записей каждого skin: имена слотов,
имена состояний (placeholders) и типы attachments, включая различие mesh/linked mesh.
Не смешивать эти записи с неявным наследованием из `default`. Это позволит клиенту
сверять каталог с реальными данными без internal-типов и повторного разбора JSON.
Области явного скрытия/замены берутся из описания комплекта, а не только из skin.

Приложение использует эти возможности в CI после каждого изменения рига, skins или
клипов. Полноту заменяющих предметов можно проверять отдельно относительно базы;
новое состояние клипа требует повторной проверки ранее выпущенных предметов.
Проверки отдельных предметов не доказывают совместимость сочетаний: каталог отдельно
проверяет занимаемые области, разрешённые пересечения и допустимые комплекты.
Библиотека сохраняет детерминированные приоритеты и не угадывает правила магазина.

### Анимация не прерывается

При успешной смене комплекта должны сохраняться текущая поза костей, активный клип,
его время/фаза, скорость, пауза и порядок рисования. Не требуются stop/start,
повторный запуск `SKAction` или возврат в setup pose со стороны приложения.

Attachment timelines должны выбирать состояния **нового** комплекта. Нельзя вернуть
снятую вещь последующим ключом старого skin. При этом смена одежды не должна отменять
собственное скрытие attachment анимацией (`name = nil`) или произвольно выбирать setup
attachment вместо текущего состояния. Обработку состояния, отсутствующего в новом
комплекте, необходимо определить явно.

Начало клипа, повтор, завершение, stop с reset и без reset не должны терять выбранный
комплект. Цветовые ключи продолжают работать по существующему контракту. Переодевание
не должно повторно отправлять уже пройденные события и нарушать завершение одноразового
клипа. Нужно учитывать смену внешности из event callback, а не только между кадрами.

### Несколько персонажей и ресурсы

Несколько `Skeleton` могут разделять один compiled asset и текстуры, но иметь разные
комплекты и независимое воспроизведение. Изменяемое состояние внешности принадлежит
конкретному экземпляру; глобальный изменяемый skin для всех фигур не подходит.

Смена комплекта не должна повторно декодировать JSON, компилировать все анимации или
создавать новый `Skeleton`. Переиспользовать существующие compiled attachments и
ресурсы, насколько позволяет выбранная реализация. Не создавать заранее все сочетания
товаров. Повторное применение того же комплекта не должно сбрасывать состояние или
накапливать renderer nodes и логические attachments.

Нужна проверка стоимости переключения и отсутствия роста памяти при многократной
смене вещей. Конкретные численные бюджеты разработчик предложит по результатам
измерений; это не требование переодевать каждого персонажа на каждом кадре.

геометрию. Вопрос гарантии идентичности выдаваемых attachment nodes после смены вещи
нужно описать отдельно от сохранения Skeleton, bones и slots.

## Цвета и ответственность приложения

В первой версии достаточно выбирать подготовленные варианты командных attachments.
Палитра игры: синий, яркий мандариновый, фиолетовый и розовый. Поддержка произвольного
tint, palette shader и material masks в это задание не входит. Если её предложат позже,
внешний цвет должен переживать reset/смену skin и сочетаться с анимационными цветами.

Библиотека не знает о ценах, оплате, инвентаре, типах пиратов и правилах магазина.
Приложение проверяет владение и совместимость предметов, выбирает команду и формирует
комплект. Оно же определяет обязательные части тела и видимые командные зоны.
Runtime предоставляет общие механизмы приоритетов/замены/скрытия, не зашивая игровые категории.

Не менять цветовой контракт существующего renderer и texture provider. Для проверочного
приложения ассеты и вывод — sRGB; смена комплекта не должна менять цвет или альфу текстур.

## Подготовка арта и контента на стороне игры

Следующие обязанности принадлежат игре; доработка библиотеки предоставляет проверку
и описание skins, но не реализует каталог, доставку контента и художественную приёмку.

- Для первого гардероба фиксируется база типа персонажа в рамках версии пакета;
  вся косметика меняется поверх неё. База не обязана быть skin с именем `default`.
  Общая транзакция смены базы и комплекта не требуется: два последовательных вызова
  до рендера не обязательно дают промежуточный кадр, но общего отката у них нет.
- Имена слотов и placeholders, их назначения и обязательные состояния фиксируются
  как контракт версии контента до производства каталога. Конкретная раскладка ещё
  должна быть утверждена в проекте игры; новая анимация не выпускается без повторной
  проверки совместимых предметов.
- По границе предлагаемого ADR скрытие применяется к слоту целиком. Детали,
  которые требуется скрывать независимо (например бандана и чёлка), разносятся
  по слотам. Командные зоны отделяются там, где им нужна независимая видимость.
  Points и bounding boxes размещаются вне сменных region-слотов: наличие такого
  состояния в базе делает всю область недоступной для композиции первой версии.
- Предметы первой версии не добавляют point, skin bones или constraints. Обычную
  дополнительную кость пера/серьги можно заранее включить в общий риг, переэкспортировав
  персонажа и перепроверив каталог. Это не поддержка условных skin bones.
- Каталог разрешает только согласованные замены командных деталей, включая детали
  нового покроя одежды. Запрещена потеря командного обозначения, а не любая замена
  командного слота. Читаемость каждой команды на поддерживаемых типах местности
  становится обязательной визуальной приёмкой арта; одной проверки метаданных мало.
- Старый клиент отображает неизвестный или несовместимый товар безопасным базовым
  вариантом, сохраняя исходный `equippedItemId` в данных экипировки. Приложение
  формирует и проверяет доступный ему комплект; fallback не стирает экипировку и
  не отменяет строгую ошибку библиотеки для некорректного входа. Совместимость
  версии каталога, рига и пакета, а также конкретные безопасные варианты задаёт игра.
- Новый предмет не обязательно требует нового релиза приложения: библиотека принимает
  JSON как `Data` и внешний texture provider, поэтому обновлённый полный пакет может
  создать новый asset. Добавить отдельную шляпу в существующий compiled asset нельзя.
  Доставка, проверка версий и замена пакетов/живых персонажей требуют отдельной работы.
- Владелец игры задаёт целевые устройства, максимальное число фигур, частоту смены
  комплекта и размер каталога со всеми командными вариантами. Разработчик предлагает
  бюджеты по измерениям времени, памяти полного asset и пика при переключении.
  Ресурсы всех skins разрешаются заранее, даже ненадетых; фактическая память зависит
  от texture provider и разделения текстур, а не только от числа активных вещей.

## Что разработчику нужно определить при подготовке решения

- Форму публичного API применения, проверки без применения, чтения состава skins
  и текущего комплекта.
  Примеры вызовов должны быть доступны приложению без доступа к internal-типам.
- Приоритеты конфликтующих записей, поведение дубликатов, пустого комплекта,
  отсутствующего `default` и пересечения replace/hide.
- Гранулярность скрытия: весь slot, отдельный placeholder или другая явная единица.
  Поведение при снятии скрытия и при отсутствии нужного animation state.
- Взаимодействие нового механизма с `apply(skin:)` / `applyDefaultSkin()` после
  композиции: ожидается предсказуемый переход к обычному single-skin режиму без
  оставшихся скрытий и частей прежнего комплекта; детали документировать.
- Гарантии для region, mesh, linked mesh, point и bounding-box attachments в композиции;
  ошибки для неподдерживаемых случаев. Расширение поддержки meshes не должно затормозить
  минимальный сценарий region-only, но его границы должны быть ясны клиенту.
- Поток/момент безопасного вызова, включая event callback, и границу атомарности
  относительно `prepareMeshes`. Не обещать потокобезопасность SpriteKit без реализации.
- Какие узлы/ресурсы можно переиспользовать, какие пересоздаются и какие внешние ссылки
  после смены предмета перестают быть действительными.
- Политику диагностики без частичного применения. Ошибка входного комплекта не должна
  превращать работающее проигрывание в скрытый или неисправный Skeleton.

Это вопросы к техническому решению разработчика, а не готовые сигнатуры или выбранные алгоритмы.

## Как будем принимать результат

| Сценарий | Ожидаемый результат |
|---|---|
| База + две шляпы на выбор + два варианта одежды + серьга | Вещи комбинируются независимо без заранее созданных полных skins. Один предмет может занимать несколько слотов. |
| Снять/вернуть серьгу, надеть шляпу поверх банданы | Явное скрытие отличается от отсутствия override; нет двойных деталей и неожиданного fallback из default. |
| Сменить вещь посередине walk и на паузе | Кости, фаза, скорость и пауза сохраняются. Все части комплекта меняются согласованно. |
| После смены наступают attachment, color и draw-order ключи | Новый комплект продолжает работать, состояние nil анимации сохраняется, снятая вещь не возвращается. |
| Repeat, новый клип, stop/reset; смена из callback события | Комплект сохраняется, нет повторных событий, сбоя completion или устаревшего action. |
| Состояние анимации отсутствует в новом комплекте | Выполняется явно документированная политика; нет случайного подставления базового предмета. |
| Неверное имя skin/слота/attachment или неподдерживаемый случай | Понятная ошибка и прежний комплект целиком; воспроизведение остаётся работоспособным. Ошибки ресурсов, возникающие ещё при compilation, проверяются на том этапе. |
| Проверка без применения и чтение skin из клиентского модуля | Публичные типы доступны без internal-доступа; те же ошибки контента, что при применении; нет изменений живого состояния или создания Skeleton/renderer. Метаданные содержат слоты, placeholders, типы и различают mesh/linked mesh. |
| В клип добавлено новое состояние заменяемого слота | Предварительная проверка выявляет неполный ранее допустимый предмет; диагностика указывает отсутствующее состояние. |
| Два Skeleton используют один SpineMeshAsset | Разные облики и независимая смена вещей, без изменения общего asset и без влияния на соседа. |
| Повторить один комплект и многократно чередовать разные | Нет сбросов позы, накопления nodes/physics objects и неограниченного роста памяти. |
| Четыре командных варианта поверх предметов | Выбранные предметы сохраняются, командная деталь меняется; категории остаются на стороне приложения. |
| Старые single-skin и legacy-клиенты | Существующий контракт не нарушен; переходы между новым и старым API документированы и проверены. |
| Region-only пример и существующие mesh/physics fixtures | Новая возможность работает в обязательном пути; текущие гарантии библиотеки подтверждены регрессионными проверками. |

Нужны автоматические проверки ключевых сценариев и небольшой запускаемый пример
переключения вещей в SpriteKit. Fixtures должны быть самодостаточными для репозитория
библиотеки, без обязательной зависимости от локального проекта пиратов. Помимо успешной
компиляции проверить реальное изображение и воспроизведение; отдельно зафиксировать
платформы и устройства, на которых выполнялась проверка, и измерения смены комплекта.

Публичная документация должна объяснять подготовку skins/placeholders в Spine,
применение и снятие предметов, приоритеты, сохранение анимации, ошибки и ограничения.
Опорные существующие тесты находятся в `Tests/SpineTests/Mesh/`: `SlotStateTests`,
`AttachmentInteropTests`, `ActionLifecycleTests`, `ResourceLifetimeTests`,
`RendererProxyLifetimeTests`, `LinkedMeshTests` и проверки physics reconciliation.

## За пределами задания

- Магазин, платежи, серверная проверка покупок и сохранение инвентаря.
- Общий риг/retargeting между типами персонажей и новые анимации для каждой вещи.
- Производство всех предметов, дорисовка скрытых частей и художественная приёмка ассетов.
- Загрузка DLC/предметов по сети, отдельные asset bundles, ленивый compiler ресурсов.
- Новые meshes/deform/constraints/clipping, смешивание анимаций и физика ткани.
- Изменение формата Spine, общего игрового gameplay/hitbox-контракта или renderer backend.
- Публичный доступ к полям `EventModel`: это отдельная задача для игровой логики событий.

Продуктовый контекст в соседнем проекте: `pirates/art/features/character-customization.md`.
Текущий region-only пример: `pirates/art/characters/sailor/` и
`pirates/art/prototype/ArtPreview/DressingRoomScene.swift`. Он содержит один базовый
skin; каталог предметов там ещё не реализован.
